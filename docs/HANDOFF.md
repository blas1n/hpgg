# HANDOFF — HPGG (hpgg.win)

Last updated 2026-09-29. Read `docs/STATUS.md` first for the current state; this file is how to operate and extend the project.

## What this is
A static Heroes of the Storm tier site, Korean by default with every UI string also in English (#10, "Localisation"). A Python collector pulls hero statistics once a day from the Heroes Profile API v1, commits JSON to `main`, and a Next.js static export (React 19 + Tailwind 4, `output: "export"`) renders the site; tiers are computed from the same JSON at build time (홈, search index) and in the browser (tier table, hero detail) with the formula printed on the page. Player search (전적 검색) is the one live feature: the page calls our own API server (`server/`, https://api.hpgg.win, Docker on the owner's Mac mini), which calls Heroes Profile with the key and caches the answers — see "Server (api.hpgg.win)". No accounts yet (#28).

- Live: https://hpgg.win/ko/hots/ (Korean, default) and https://hpgg.win/en/hots/ (English) — GitHub Pages + custom domain, HTTPS enforced; `data/CNAME` is published with the site so the domain survives every deploy. Root `/` forwards to the stored language choice, else `/ko/hots/`; the URLs from before #10 (`/hots/…`) forward too. A second game would live at `/<locale>/<game>/`.
- Brand: hpgg.win — Happy Good Game. Logo, crops and palette in `docs/BRAND.md` and `data/img/brand/`.
- Analytics: https://hpgg.goatcounter.com — page views. (👍👎 voting was removed 2026-09-28; formula feedback goes to contact@hpgg.win.) **Continuity**: since #10 (2026-09-29) page paths are `/ko/hots/…` and `/en/hots/…`; before, Korean pages counted as `/hots/…`. To compare over time, add `/hots/<page>` and `/ko/hots/<page>` (and `/en/…` for all visitors). The forwarding pages carry no counter, so a visit through an old link counts once, on the new path.
- Repo: https://github.com/blas1n/hpgg (public). Bot commits land on `main`; raw daily snapshots on the orphan `snapshots` branch.
- Design of record: `docs/DESIGN-2026-09-28.md`. E2E checklists: `docs/e2e/`.

GitHub Actions (that dispatch, cron 05:20 KST as fallback, plain workflow_dispatch, push:main)
  gate job (cron / if_stale): data/latest collected < 12 h ago → stop (python3 -m collector.freshness)
  collect job (cron/dispatch only, not after a fresh gate)
    uv run python -m collector
      GET /v1/patches                       → newest build with valid_globals
      12× GET /v1/heroes/stats?group_by_map&region=KR|NA|EU → qm, sl, sl_low(1-4), sl_high(5-6) per region (60 s apart)
      12× the same with groupsize=Solo      → party correction of each (every row, per map too)

      1× GET /v1/heroes/talents/builds/all  → popular builds, qm+sl combined                    (7/week cap!)

  Every action is pinned to a commit; tests/test_workflows.py fails on a tag, on the key in another job, or on a

## One reference patch (owner 2026-09-29)
The whole site shows ONE patch: every page, both modes, brackets, regions, the talent builds, the matchups and the 밴픽 simulator. It is decided once per run by the collector (`collector/snapshot.py` `reference_patch`, written to `meta.json` as `reference_patch`): the previous patch while the current one is thin in Quick Match **or** Storm League (under half the heroes over the 200-game floor), else the current one. Brackets and regions never decide it.
- The collector collects the builds and the matchups **for** the reference patch. **The region of the day** (2 calls) goes to the reference patch first; while that is the previous patch — final, it never changes — a region already in `data/previous/` is not fetched again and the day's calls build the current patch's region in `data/latest/`, so it is there when the current patch becomes the reference (`_region_patch`, owner 2026-09-30). Until 2026-09-30 regions were collected on the current patch only, so with 2.55.17.98025 as the reference every region view was empty.
- A stats call returns the whole patch so far (no date filter): each run replaces the file with a larger total; a finished patch's files are final. The answer has no region column, so a region needs its own call (`region=`); summing regions into the whole costs more calls, not fewer. Talent builds are the whole only (owner 2026-09-30): `/heroes/talents/builds/all` does take `region` and `league_tier`, but its cap is 7/week.
- The web never decides: `referencePatch(meta)` / `referencePatchId(meta)` (`web/src/data.ts`) read it; `pickShown` shows the reference patch's file for every view, and a view with no valid file on it shows nothing (the tier table says "패치 X에는 이 보기의 데이터가 없습니다") — never another patch in its place. `onReference` drops a builds or matchups file of another patch (`readBuilds`, `readMatchups`, `loadMatchups`).
- **A patch is a regular patch with its hotfixes** (owner 2026-10-01, replacing "a patch is one build" of 2026-09-30): the patch id is x.y.z (`2.57.0`), and every HP call asks for all its queryable builds at once — `timeframe_type=minor&timeframe=2.57.0.98285,2.57.0.98304` (HP sums them; verified live 2026-10-01: SL 4,550 matches for the two builds vs 1,526 for 98304 alone, the same numbers hotsgg.com shows for "2.57.0"). `choose_patch` → the x.y.z of the newest settled build; `timeframe_of(patches, patch)` → its builds, oldest first (a four-part id from before 2026-10-01 is its own timeframe, so `previous/` 2.55.17.98025 still resolves). A hotfix build joins the current patch: no rotation, `patch_started_at` stays, matchups stay on their 2-day gate. HP's `major` takes x.y (`2.55`, every 2.55.z since 2024), not x.y.z — `major` + `2.57.0` is `422 invalid_parameters`; do not use it. Why the owner chose this: the site sat on 2.55.17.98025 for days after 2.57.0 shipped because a one-day hotfix (98304) restarted the sample, while other HP-based sites already showed 2.57.0. What it trades: unannounced hotfixes (2.55.17.97650 changed seven heroes, 97771 Chromie) are now averaged into their patch; the hero page's hotfix list still shows them per build.
- **Only a healthy patch becomes the previous patch** (`healthy` in `collector/snapshot.py`): when the patch changes, the outgoing one moves to `previous/` only if it was not thin in QM and SL; a thin one is dropped and the previous patch stays. A build of the new patch (meta before 2026-10-01 said `2.57.0.98304`) is the new patch itself, never promoted. `commit_atomic` rotates only when `build_meta` promoted.
- **A new build settles for an hour** (`PATCH_SETTLE`): HP lists a build before its stats accept it (patch list and filter options are separate 10-minute caches) — the 2026-09-30 03:20 run got `422 invalid_parameters` seven minutes after 98304 appeared. Builds listed less than an hour before `collected_at` are left out of the timeframe (and a new x.y.z whose only build is unsettled is not chosen yet).
- The one override is the reader's: the tier table's "현재 패치 보기" (`?patch=current|previous`).
- A region's own thinness (`thinSample`, `#region-note`) is a warning only.
- Before 2026-09-29 each file decided for itself (the tier page per file, matchups by SL, builds on the current patch), so a hero page showed 2.55.17 stats next to first-day 2.57 builds (5 builds, 12 games in all for Illidan).

## The formula (web/src/formula.ts — printed on the page)
```
WRc   = WR + (WRsolo − (pooled_solo − 50) − WR) × m / (m + 1000)   party correction (#36), QM + SL overall only
WRs   = 50 + (WRc − 50) × n / (n + 500)                shrink small samples toward 50
score = pick% × (WRs − 50) × 3 + ban% × 1              multiplicative; QM has no ban term
tiers = heroes with n ≥ `min_games_for_tier` (collector `MIN_GAMES_FOR_TIER`, 50 since 2026-10-01 — owner: tune as samples allow; patch health stays on `PATCH_HEALTH_GAMES` 200) (and in heroes_ko.json — see below), sorted by score, cut at cumulative 6/24/54/82/94 % → S/A/B/C/D/F
        boundary_i = min(N, max(floor(share_i·N), boundary_{i−1}+1))  (monotonic, ≥1 per tier)
```
Why multiplicative: an additive formula ((WRs−50)+0.15·pick+0.15·ban) reproduces HOTS GG and promotes low-win-rate popular heroes (Brightwing 47.6 % WR → A); 45/90 heroes change tier between the two on the 2026-09-28 fixture (DESIGN-2026-09-28.md). **One formula, no name** (owner, 2026-09-29): the formula presets (#2) were removed — the site prints the formula as maths and never under a person's name (the YouTuber video it came from is a reference in the design doc, not the formula's name). `FORMULA` in `web/src/formula.ts`; `e2e/tierlist.spec.ts` checks there is no formula selector. Tier-table filters: mode, role, region, and in Storm League bracket and map. An old `?preset=` link opens the default view and drops the parameter.

**Party correction (#36, owner 2026-09-29).** Premade groups win more, so heroes popular in stacks look stronger than they are for a solo player. The collector (`collector/party.py`) makes a `groupsize=Solo` twin of every Heroes/Stats call (the hero player's own party size, HP table `global_hero_stack_size`) and writes `tier_win_rate` (WRc above; m = the hero's solo games, WRsolo re-centred so all solo games together are 50 %) on every row of every view — each map by its own solo rows and pooled rate (owner 2026-10-02: the correction is part of the formula, so it is everywhere) — plus a `party` block {k, solo_pooled, solo_games}. `scoreRow` reads `tier_win_rate ?? win_rate`, so every tier (홈, 영웅, 상세, 전장, 티어표) uses it with no call-site wiring; the win-rate column stays uncorrected. The printed formula adds the correction only when the view's rows carry it (`appliedParty`) — since 2026-10-02 every view carries it. A failed solo call fails the run (`run.party_failed`, owner 2026-10-01: tiers without the correction are a different ranking under the same name — rather no update): yesterday's corrected files stay, no matchups that day; `--previous` likewise writes nothing. `--previous <build>` backfills the correction too. Why this form: `Global/Party` breaks down one hero per call (90 > 70/week); solo-only win rate halves the sample (a same-size random subsample alone moves ~20/90 tiers); the shrunk adjustment keeps the full sample. Measured on 2.55.17 QM: pooled solo 48.63 %, 28/90 heroes change tier (Garrosh −5.7 %p solo vs all, Ana −5.1, E.T.C. −4.4); Cho'gall has no solo games and is uncorrected. Full numbers: issue #36.

## 주간 메타 리포트 (/hots/meta/, owner 2026-10-05)
One issue a week, Monday–Sunday KST, kept as an archive (`/hots/meta/<yyyy>-w<ww>/`; `/hots/meta/` is the newest).
- Heroes Profile's stats are cumulative over the patch, so a week is the difference of two daily records of one patch. Every run writes `data/history/<KST day>.json` (whole QM/SL: each hero's cumulative games, wins, bans and solo games/wins, ~8 KB) and then `collector/weekly.py:build_weekly` writes any issue the day closes: `data/weekly/<week>.json` + `index.json`.
- An issue closes on the Monday dawn record after its week (or one within two days). It opens on the Monday record of the same patch (kind `week`, baseline = the week before). In the week a patch started there is no such record: it counts everything of the patch up to the closing record against the previous patch (kind `patch_start`, baseline = `data/previous`, all-maps rows).
- The week's rows get the same party correction as the site (`party.apply_party_correction` on the window's solo counts). Issues are never rewritten.
- The page (`lib/weekly.ts`, `components/weekly/WeeklyView.tsx`): 요약 3줄, this week's tier top 10 with rank change, climbers/fallers (5 each), new heroes, daily win-rate lines (a day under 20 games is a gap). QM/SL toggle (each mode is its own numbers).
- First issue 2026-w40 (2.57.0's first week) was backfilled from the `snapshots` branch with `tools/backfill_history.py`; its window equals that day's site data exactly (all 91 heroes, both modes). Records before 10-02 use the old one-build patch and cannot be differenced.
- Weekly community post: link the newest issue each Monday.

E2E: the section's own spec skips itself (`test.skip(!FEATURES.x)`), page lists filter with `sectionEnabled`, and `e2e/launch.spec.ts` checks the switched-off state (no menu link, 404, not in the sitemap). Tests and e2e were run with the flag both ways when it was added. A new feature: add it to `FEATURES` and `SECTION_OF`.

## 밴픽 simulator (/hots/draft/, #25) — switched off, see above
- **Order**: the Storm League draft — ban A, ban B, ban A, ban B · A · B B · A A · ban B, ban A · B B · A A · B (A = first-pick team). Sources: Heroes Profile's drafter (`resources/js/components/Drafter/Drafter.vue`) and a recorded draft (`resources/api-fixtures/replay_draft.json`); HP's repo has no licence, so only the order is used. Cho'gall: one half fills the same team's next slot, so the pair is offered only where that team picks twice in a row (the rule reproduces HP's excluded steps 4, 6, 8, 12, 14, 15; `tests/draft.test.ts`); banning a half takes both.
- **Suggestions** (owner: candidates only, no team score or win probability): `score = (WRs − 50) + Σ allies' gap with h + Σ −enemies' gap against h + map gap`, each term shown per row; gaps × n/(n+100), pairs under 50 games left out (the hero page's rule). WRs is the tier table's input (party-corrected, k=500) from the shown Storm League snapshot; pair gaps come from the **picked** heroes' `data/matchups/<slug>.json`, fetched in the browser; a picked hero without a file is named under the list. Ban suggestions = the same score for the other team.
- `web/src/lib/draft.ts` (pure: order, availability, Cho'gall, undo, recommend, link), `components/draft/DraftView.tsx`; link `?first=them&map=<name>&d=slug.slug…` is replayed through the rules. The first-pick toggle is fixed once a hero is chosen.

### Matchups (counters / synergies, #15)
- `collector/matchups.py`. Storm League only (owner, Basic plan). One call per hero; recorded answer in `tests/fixtures/live_probe_matchups_abathur_sl_2.55.17.98025.json.gz`: `{ally, enemy, combined}`, one row per other hero with `wins`/`losses`/`games_played` from the asked hero's side — but on `enemy` rows `win_rate` is the asked hero's **loss** rate, so the collector recomputes every win rate from wins/games. `combined` is not stored.
- **Gate (per hero file)**: due when the file is missing, is for another patch, or was collected ≥ 2 calendar days (UTC) ago. A failed, quota-stopped or time-boxed round leaves the other files as they are and those heroes are simply due again tomorrow. Matchups never fail the run.
- **Patch**: the reference patch (see "One reference patch"), like everything else.
- **Ranking** (`web/src/lib/matchups.ts`, printed on the page): score = (pair win rate − the hero's own win rate in the same sample) × n/(n+100); pairs under 50 games are left out; top 5 enemies with the lowest score (상대하기 어려운 영웅) and allies with the highest (잘 맞는 영웅). The page shows the unshrunk gap (%p) and games.
- Pages show the section in both modes, labelled 폭풍 리그; without a file the section says the data comes with the next collection.

### Regions × brackets (아시아 / 아메리카 / 유럽, #14; the cube since 2026-10-02)
- Owner decision (2026-10-02, Intermediate): every view in every region, daily — KR / NA / EU × (QM, SL, 브실골플, 다마그), each with its solo twin (24 Heroes/Stats calls; `CELL_SPECS`, `CELL_SOLO_SPECS`). Before, on Basic, one region a day for QM + SL only, and region × bracket was not collected.
- **The whole is the sum of its regions** (`collector/snapshot.py` `sum_regions`): a game is played on one server, and CN closed in 2023. Checked on 2.55.17.98025: KR + NA + EU reproduced the global file's wins and losses for all 1,440 QM and 1,170 SL (hero, map) rows; bans (derived from HP's rates) within 13 on a row, ban rate within 0.04 %p. Rates are recomputed against the summed matches (a map's: Σ games on it / 10); `ci` is None on summed rows. Brackets are **not** summed: a game counts in the bracket of each of its players.
- Files `data/latest/{qm,sl,sl_low,sl_high}_{kr,na,eu}.json` (`"region": "KR"` …) next to the whole (`"region": null`). Any failed call fails the run — a whole without one region, or a view without its correction, would be a different number under the same name — and yesterday's files stay. `--previous <patch>` collects the same cube (24 calls); `--only qm,sl` QM and SL in every region (12).
- HP takes `region` and `league_tier` together (probed 2026-10-02: KR SL 820 hero-games, KR 브실골플 482). Small regions are thin: KR SL had ~82 matches on 2.57.0 after three days.
- A region file is a different cohort (`lib/cohort.ts`): no ▲▼ against the global file; a region's thin sample is judged by its own `heroes_ranked` — heroes over the tier floor (`#region-note` warns). CN closed in 2023 and is not collected.
- **Pages** (owner 2026-10-02: "KR 저티어 구간만 보기"): the tier table's region and bracket selects combine (`snapshotKey(mode, bracket, region)` → `sl_low_kr`; QM has regions only) and both stay in the URL (`?mode=sl&region=kr&tier=low`); a region or bracket view prints its sample note (`#region-note`: label, date, heroes over the floor, thin warning); a cell not collected is "수집 전" in the menu. The hero page has the same filters (`#hero-region`, `#hero-bracket`, same URL names) driving the stat cards and per-map rows, and one 지역 × 구간 grid (`#grid`, a cell sets the filters; QM: one column) in place of the old 구간 / 지역 sections; every cell's summary is pre-rendered into the page (16 per hero). Talent builds and matchups stay on every region and bracket and say so ("전체 지역·구간 기준") when a filter is set.

## Hotfix watcher (unannounced builds, #62)
Blizzard ships balance hotfixes without notes (2.55.17.97650: Chen, Gall, Chromie, Yrel; 2.57.0.98304: Auriel). The watcher runs on the Mac mini every 30 minutes: launchd `com.blas1n.hpgg-hotfix` (`tools/hotfix/com.blas1n.hpgg-hotfix.plist`) → `uv run python tools/hotfix_watch.py` in its **own clone `~/Works/hpgg/bot`** (never `main/` or a dev worktree: it pulls, commits and pushes itself). Log: `~/Library/Logs/hpgg-hotfix.log`.
- **Flow** (`collector/hotfix_watch.py`): Ribbit `us.patch.battle.net:1119/hero/versions` → new build? → list it with `tools/hotfix/bin/casccdn` (CascLib, list only, ~150 MB downloaded and deleted) → hero XML whose content hash changed since the last build seen → fetch only those by byte range (`collector/cdn.py`, MD5-checked) → `collector/hotfixes.py` → `data/hotfixes.json` → commit + push to main (deploys). The first run only remembers the build (`data/.tmp/hotfix/state.json`, listings in `listings/`).
- **What is shown** (parser 3): numbers old → new, grouped like the notes — **base stats** in the game's own words (생명력 / 생명력 재생량 / <energy> / <energy> 재생량 from `lifetype`/`energytype`; 일반 공격력, 공격 속도 (attacks per second, from the weapon's period), 일반 공격 사거리 from the game strings), **abilities** as `name [Q/W/E/R/D]`, then **talents**. Owners are resolved talent first (an ability id starts many talent entries), then the unit/weapon (`CUnit` = `game.unit`, `CWeapon*` = `game.weapons`, `CEffectDamage` = the weapon's `DisplayEffect`), then the ability with the longest id prefix. The ids come from `data/talents/<slug>.json` → `game` (`tools/build_assets.py`). Numbers nobody claims are left out; a number changed the same way outside every owner too is left out as well (Mal'Ganis's 흡혈의 손길 leech sits on every damage effect: shown nowhere rather than as three talents). A build an official note belongs to shows as the note.
- **Checked against the 2.57 note** (97771 → 98304, parser 3): every base and ability line the note has matches except Mal'Ganis's trait (above) and one Qhira line; 13/13 talent numbers. Extra (unannounced within 2.57): Mal'Ganis 지옥 발톱 [Q] 0.2 → 0.15, 괴저 기운 [W] 0.2 → 0.3.
- **Re-deriving**: `uv run python tools/hotfix_backfill.py <versions…>` lists each build again from `tools/hotfix/builds.json` (BuildConfigs from BlizzTrack; add rows for new builds) and rewrites their records — run it after a parser change (~10 min for seven builds).
- **Setup** (done 2026-09-30): `git clone https://github.com/blas1n/hpgg.git ~/Works/hpgg/bot && cd ~/Works/hpgg/bot && uv sync && tools/hotfix/build.sh`, then install the plist (its header). Moved from `~/Works/hpgg-bot` on 2026-10-01. Clone over HTTPS: pushes use the `gh` credential helper (no SSH key on the Mac mini). CascLib is pinned in `build.sh`; cmake comes from `uvx`.
- **Traps**: never extract with CascLib (whole 256 MB archives: 13 GB in the spike). The current CDN config's archives resolve old builds' files; an old CDN config can 404. Old build configs: BlizzTrack `blizztrack.com/api/manifest/hero/seqn?file=versions&page=N` (needs a browser User-Agent).

## Server (api.hpgg.win)
HPGG's application backend. Today it serves player search; accounts (#28, Battle.net login) and community (#7) are meant to land here as further feature modules, not as new services.

```
browser (hpgg.win/ko/hots/players/?tag=Name%231234&region=KR)
  → GET https://api.hpgg.win/v1/players?battletag=Name%231234&region=KR
  → Cloudflare (TLS, CF-Connecting-IP) → cloudflared tunnel → 127.0.0.1:8800 on the Mac mini (bsserver)
  → container hpgg-api (FastAPI/uvicorn :8000) → SQLite cache → Heroes Profile GET /players (Bearer, server-side only)
```
- **Shape**: `server/app.py` `create_app(settings)` — CORS allowlist, JSON error envelope `{"error": {"code", "message"}}`, one structured log line per request, `/healthz`, then one router per feature (`server/players/router.py`). A new feature = a package with its router, tables on `server.db.Base` (imported in `server/models.py`) and an Alembic revision.
- **Persistence**: one SQLite file (WAL) on the named volume `hpgg-api-data` (`/data/hpgg.sqlite`), SQLAlchemy async (aiosqlite), schema only through Alembic (`server/migrations/versions/`, applied at startup; `tests/server/test_db.py` fails if models and migrations drift). Why SQLite and not Postgres: one process on one Mac mini, a small write load (cache rows, later accounts/comments), nothing to operate or back up beyond one file; moving to Postgres later is a driver/URL change plus a data copy, because everything goes through SQLAlchemy and Alembic. The player cache lives in the same database (tables `hp_cache`, `hp_quota`, `hp_daily_usage`, `hp_private_player`, `hp_feed_cursor`) — one volume, one backup.
- **Heroes Profile attribution (API terms §4, HP 2026-09-29)**: every page shows `HpCredit` ("Data provided by Heroes Profile", linked) in body text on the first screen. It belongs to the page title and shares its line (`components/PageHead.tsx`, #77 — on a line of its own above the title it read as a line slapped under the header); 영웅 상세 and 전장 상세 draw their title beside a portrait and inside a banner, so they place `HpCredit` themselves, top right. Sharing the title's line costs no vertical room, which is why `<main>` keeps its old `mt-6` and the tier table still has 14 rows above the fold at 1280×900 (`e2e/density.spec.ts`). The credit is `whitespace-nowrap`: broken over two lines it reads as a fragment. The footer credit is extra, not enough on its own. What may never change is checked in `e2e/attribution.spec.ts` (9 pages × 390/1280).
- **Uploading replays**: only through HP's embeddable widget (`lib/hpUpload.ts`, iframe `Upload/Embed?source=hpgg`, messages trusted only from `https://www.heroesprofile.com`). HP asked us not to call `replays/fingerprints` and not to relay uploads through our server. Record of the exchange: `docs/outreach/2026-09-29-heroes-profile-upload-cors.md`.
- **Player search**: one HP call per new player — `/players` (bucket *Player*, 10,000/week) returns account level, win rate, KDA, MVP, current MMR + league per mode (`*_mmr_data`), top-3 heroes/maps and the last 5 matches with MMR change (`matchData`), so the page needs no other endpoint. The server trims the ≈30 KB answer (talent objects) to a compact profile (`server/players/profile.py`, shape in `tests/server/fixtures/v1_players_200.json`, recorded 2026-09-29).
- **Quota guard** (`server/players/service.py`): fresh cache 6 h (not-found 10 min) → identical concurrent lookups share one call → live call only while HP's `X-HP-Quota-Remaining` > `QUOTA_FLOOR` (200) and today's live calls < `DAILY_LIVE_BUDGET` (1,300 per UTC day). Otherwise, or after a 429 `quota_exceeded` (until its Retry-After), the page gets the cached profile marked `stale` with `notice: "quota_exceeded"`, or a 429 `quota_exceeded` ("오늘 조회 한도 초과") for a player never seen. HP 5xx/timeouts → cached profile with `notice: "upstream_unavailable"`, or 503. `/healthz` shows the last quota reading and today's live calls. `X-HP-Quota-Reset` is seconds until the window frees up (measured).
- **Match list** (`GET /v1/players/matches`, `server/players/matches.py`): HP `/players` carries only the newest **5** games (`matchData`), which is why the page showed five. The list comes from `/players/matches` instead — up to 100 games with the stat line (K/D/A, hero/siege/structure damage, healing, damage taken, XP, deaths time, camps, level), the seven talents (`talent_name`, the key of `data/talents/<slug>.json`) and the MMR after each game. It is the small bucket (250/week on Basic, owner 2026-10-01: stay on Basic): daily budget 34, floor 10, cached 6 h. A cold query answers 202 and is asked again every 2 s for up to 20 s (not charged). Past the budget, a full list HP returned < 24 h ago is served stale; else `/players/mmr/history` for the player's most played game type (10,000/week) gives the games with hero, map (HP map id → `server/players/hp_maps.json`), result and MMR, `source: "basic"`, cached 1 h so a full list replaces it. Same privacy rules as the profile (both cache keys dropped). Answer: `{source: "full"|"basic", matches, fetched_at, stale, notice}`; `/healthz` shows both buckets.
- **Match list on the page** (`web/src/lib/matches.ts`, `components/players/MatchHistory.tsx`): fetched next to the profile (its own call, 30 s timeout for HP's job queue); briefing over the newest 20, MMR line of the most played mode, rows 20 at a time; talent names/icons from `talents/<slug>.json` per hero on screen. If the call fails the profile's 5 games stay (old card). Score labels come from the game's GameStrings (`ScoreValue/Name/*`, ko + en); to read them again, list a build with `tools/hotfix/bin/casccdn` and fetch `mods\heroesdata.stormmod\<loc>.stormdata\localizeddata\gamestrings.txt` with `collector.cdn.fetch_files`.
- **One game in full** (`GET /v1/replays/{id}`, `server/players/replays.py`; web `lib/replays.ts`, the ▾ on a game card): HP `/replay/{id}` — both teams, each player's BattleTag (links to their search), hero, award, MMR change, score line and talents, game length, parties (HP names them by a colour word; the page only groups them, never uses the word as a colour). Fetched only when a card is opened; cached ≤ 24 h (it names ten players) and every answer drops players in `hp_private_player`. **Awards**: `tools/build_awards.py --build <heroes-data build>` writes `data/awards.json` (game key → ko/en name, icon), `data/img/awards/` (64 px) and `server/players/hp_awards.json` (HP `award_id` → game key, from the ids recorded in `tools/hp_awards_seen.json`: 16 so far). An id the shipped table lacks is **learned by the server** (`server/players/awards.py`): a `/replay` answer carries the award's title and icon, they are matched against `server/players/game_awards.json` (title first — HP sends the Avenger icon with Bulwark — then icon) and kept in table `hp_award_map` (`awards.learned` in the log). Match lists keep HP's `award_id` and are named when served, so a learned id reaches lists cached before it. Only an award the game data itself lacks stays unnamed (`awards.unresolved`): then rerun the tool with a newer heroes-data `--build`.
- **Stats per hero** (`GET /v1/players/heroes?mode=all|qm|sl`, `server/players/heroes.py`; web `lib/heroStats.ts`, `components/players/HeroStats.tsx`, #88): HP `/players/heroes` (bucket `player_hero_all`, 500/week on Intermediate) — one row per hero the player has on Heroes Profile: games, win rate, KDA, per-game averages (K/D/A, hero and siege damage, healing, damage taken, experience). Every game type unless `game_type` narrows it; each mode is its own cache entry (6 h; stale up to 24 h past the budget, then `quota_exceeded`), dropped with the player's other entries when they go private. The section asks only when scrolled into view and a mode only the first time it is shown, so a search alone costs nothing from this bucket. Players met often (HP `friendfoe`) is left out (owner 2026-10-02).
- **Player privacy (API terms §5, #74)**: HP refuses a private player (`403 player_unavailable`), but cannot reach what we already cached, so that half is ours: poll HP's privacy change feed at least every 24 h, stop showing and delete a player within 24 h of them going private, honour a takedown HP passes on within 7 days. `server/players/privacy.py` polls `GET /players/privacy/changes` at startup and every hour (`PRIVACY_POLL_SECONDS`; own bucket, 10,080/week), cursor `since` + `after_id` in `hp_feed_cursor` (written with each page, in one transaction), private players in `hp_private_player` (region + lower-cased tag). A private player gets `403 player_private` ("비공개 프로필입니다") from no cache and without asking HP; a `403 player_unavailable` from HP marks them private too, so it is never mistaken for an outage that serves the stale copy. Every poll also deletes cached answers HP returned more than 24 h ago (`STALE_MAX_SECONDS`), and no profile older than that is ever served, so nothing outlives the rule even while the feed is down. `/healthz` → `privacy.last_ok_at`: older than a couple of hours means the poller is failing (`privacy.poll_failed` in the log). The first sync (no cursor) returned 662 changes / 642 private players on 2026-10-01. **A takedown passed on by HP** (by mail, within 7 days): `docker --context colima exec hpgg-api python -c "import asyncio; from pathlib import Path; from server.db import Database; from server.players.store import HPStore; asyncio.run(HPStore(Database(Path('/data/hpgg.sqlite'))).mark_private('<KR|NA|EU|CN>', '<Name#1234>', 'takedown'))"`. Checklist: `docs/e2e/server-privacy-checklist.md`.
- **Abuse**: 20 requests/min per visitor IP (`CF-Connecting-IP`, sliding window, in memory); inputs validated (BattleTag `name#digits`, region KR/NA/EU/CN, unknown params rejected); 404s from HP are free, so random tags cost nothing.
- **Never** log or return the HP key or the Authorization header (`tests/server/test_app.py` asserts it on every error path).

## Localisation (#10)
- **Text**: every UI string is in `web/src/i18n/ko.ts` (default) and `en.ts` — page titles, meta descriptions, formula text, empty/error/quota states included. `en.ts` is typed as the Korean table, and `tests/i18n.test.ts` fails on a missing or extra key, a different function arity, an empty message, any Hangul in English, or copy-rule words (voting, "gut feel") in either language. `tests/hangul-guard.test.ts` parses every `.ts/.tsx` under `web/app` and `web/src` with the TypeScript parser and fails on Hangul in any string, template, JSX text or regex outside the two tables (comments may be Korean); its control plants violations in memory. Messages are plain strings or functions that only interpolate; `en.ts` has a small `plural` helper.
- **Names**: the tables keep their Korean field names; `src/i18n/names.ts` swaps the display fields at the read boundary (`readHeroes(locale)`, `readMaps(locale)`): on English pages `ko`/`role_ko` carry the English game names and `alt` keeps the Korean name searchable (Korean and 초성 search still work there). Talents: `heroBuilds(…, locale)` picks `en`/`desc_en`/`cd_en`. `clean_desc(raw, "en")` prints per-level scaling as `108 (+4% per level)`.
- **URLs (decided 2026-09-29, owner)**: every language is **pre-rendered** under its own prefix from one route tree: `/ko/hots/…` (default) and `/en/hots/…`. Pre-rendered rather than a client-side switch because every language gets its own crawlable, shareable URL with `<html lang>` right in the HTML, `hreflang` alternates (one per language, `x-default` = Korean) and a canonical per page (`alternates()` in `src/i18n/locale.ts`, set in every page's metadata), and there is never a flash of another language (a static export has no server to pick one). All languages under a prefix, Korean included (owner), so no language has its own route files; the old Korean URLs forward (above). Cost: `dist` 35.9 MB → 61.5 MB (each language ~24.5 MB of HTML/RSC; data, images and JS are shared; forwarders 0.5 MB). GitHub Pages allows 1 GB.
- **Adding a language**: add it to `LOCALES` in `web/src/i18n/locales.ts` (the one list: route params, hreflang, the redirect hint, forwarders and the 404 all read it), add `src/i18n/<locale>.ts` typed as `Messages` and register it in `messages.ts`, and add the data fields named after the locale (`<locale>` on heroes/roles, `<locale>`/`desc_<locale>`/`cd_<locale>` on talents via `tools/build_assets.py`, `<locale>` objective in `maps_meta.json`; a missing field falls back to the English API name or the Korean objective, said on the page). No route files. The header switch cycles to the next language; with a third one make it a menu.
- **Switch** (`#lang-toggle`, `LanguageToggle.tsx`, next to the theme toggle): a plain link to the same page in the other language (labelled in that language, `hreflang`); a click carries the query and hash (mode, map, section stay) and stores the choice in `localStorage["hpgg-locale"]` (try/catch; if the write fails the old hint is removed, so it can never bounce the visitor back). The stored choice is only a redirect hint: an inline `<head>` script on every page sends a visitor who chose another language to that language's URL before anything paints, and the forwarders and `/` go straight to it. No choice = Korean, no redirect; the browser language is never guessed. The 404 page (one `404.html` for every missing path) speaks every language.
- **Game modes on the player page** (were guessed, now sourced): Unranked Draft = 일반 선발전 (Blizzard news 2016-06-01, 일반 선발전과 등급전 개편 관련 정보, news.blizzard.com/ko-kr/heroes-of-the-storm/20131413), ARAM = 무작위 영웅 대전 (Korean patch notes 2020-09-10, news.blizzard.com/ko-kr/article/23513939). The heroes-data game strings carry no mode names.
- **ARAM map names**: Braxis Outpost 브락시스 전초기지, Lost Cavern 잃어버린 동굴, Silver City 은빛 도시 from the game strings' reward-portrait names (kokr/enus, "<map> Portrait"); Industrial District is not in the game strings; 공업 지구 is Blizzard's own Korean name for it, from the weekly brawl posts that ran the same map (Overwatch-themed single lane, Volskaya) before it joined ARAM: "2019년 1월 11일 주간 히어로즈 난투: 공업 지구" (news.blizzard.com/ko-kr/article/22863336; en-us counterpart "Heroes Brawl of the Week, January 11, 2019: Industrial District"), and the 2018-01-12, 03-23, 08-17 and 10-12 posts.
